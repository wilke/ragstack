# RAG Repo Comparison: ragstack vs siblings

ragstack (v0.2.0 @ 4d28ac5) is a contract-first, polyglot RAG scaffold: a strong OpenAPI 3.1 contract, a cross-language (Python/FastAPI + Go/Chi) black-box conformance suite, a protocol-driven adapter layer (`protocols.py`), and one real-but-CLI-only Qdrant path. Its *engineering rigor leads the entire sibling set*. Its *RAG substance is mostly stubbed*: no LLM/generation, no wired hybrid retrieval, no real BM25, no knowledge graph, no durable persistence, no async orchestration, no auth. This report maps which siblings fill which of those gaps.

## TL;DR — the 5-bullet bottom line

- **Wire generation now (P0).** ragstack's `/v1/query` returns a literal `[LLM not yet wired]` placeholder and its rewriters call a non-existent `llm_client.complete`. **distllm** (`distllm/generate/generators/`: LLMGenerator protocol + vLLM/LangChain/HuggingFace backends + `RagGenerator`) and **ExaForge** (`client.py` + `endpoints.py`: a tested async, retrying, multi-endpoint chat client) both *have working code* that fixes this. Take distllm's generator protocol + RagGenerator orchestration; take ExaForge's pool/client as the resilient transport beneath it.
- **Get a real LLM transport for free.** ExaForge's `EndpointPool`/`InferenceClient` (health checks, round-robin/least-loaded, global semaphore, exponential backoff, errors-as-data `ChatResponse`) is nearly drop-in behind ragstack's `Embedder` protocol and the new LLM client. Also lift `_extract_json` (qa_generation.py) and `lustre.atomic_write` verbatim.
- **Fill the sparse-retrieval hole without standing up Elasticsearch.** ragstack's lexical side is bag-of-words Jaccard (explicitly "NOT real BM25"). **rag_api**'s working TF-IDF path (Arrow vocab/idf + regex tokenizer + faiss `IndexFlatIP`) and **embedding_app**'s `TfidfEmbeddingProcessor` are real sparse baselines. Port one behind ragstack's `TextIndex` protocol. (Caveat: TF-IDF ≠ BM25 — a stopgap, not the ES target.)
- **Borrow the config-as-registry pattern across the board.** distllm's `name->(Config,Impl)` STRATEGIES + discriminated-union Pydantic config, ExaForge's `Field(discriminator='name')` registries, and GoWe's keyed `Executor` registry all turn ragstack's imperative `deps.py` backend selection into declarative, reproducible YAML. Low effort, high leverage, complements (not replaces) `protocols.py`.
- **Persistence + async orchestration is ragstack's deepest unbuilt gap; GoWe is the donor.** `list-documents` returns `[]` and `ingest-status` is a stub. **GoWe** ships a working pure-Go SQLite `Store` (WAL + idempotent migrations), a tick scheduler, broker-free capability/affinity `CheckoutTask`, SSE-over-polling, and real auth — all the things ragstack only plans (Postgres/Celery/streaming/auth). Borrow patterns; don't import the engine.
- **Ignore wholesale integration of every sibling.** All five are architecturally mismatched parts donors, not components to wire in. Keep ragstack's OpenAPI contract + conformance suite as the core differentiator; never point the conformance suite at a sibling or adopt a sibling's API surface to replace the contract.

## Per-repo verdict

### embedding_app (BV-BRC Embedding / RagDB module)
**What it is:** An untested batch-CLI research tool for embedding corpora (Faiss + Arrow/HF datasets), with a known schema-key bug (`embedding` vs `embeddings`), a stubbed folder TF-IDF path, and no CI.
**Useful (working code to lift):** token-budget batching + index-sort guard in `get_embeddings_from_endpoint` (`lib/embedding_utils.py:183`); embedding-similarity semantic chunker `semantic_chunk_text` (`lib/semantic_chunking.py:127`, MIT-derived); L2-normalize+`IndexFlatIP` Faiss recipe (`build_faiss_index`, `:421`); fail-soft `(results, errors)` ingestion (`embed_document`, `:286`).
**Fills:** working Faiss index; token-budget-aware batching (ragstack's `OpenAIEmbedder.embed()` sends the *entire* list in one unbounded `/v1/embeddings` call — will blow model context on large ingests); semantic chunking; a deterministic offline sparse (TF-IDF) baseline.
**Overlap:** loses to ragstack on rigor/tests/contract and ingestion orchestration; wins on chunking variety and sparse retrieval; complementary on embedding client and vector indexing.
**Verdict: BORROW (parts donor).** Lift the four named functions behind ragstack's protocols. Do NOT adopt its assembled pipeline — you'd import its defects. The token-budget batching primitive is the single highest-value, lowest-effort grab (real correctness/scale fix for `embedders.py:54-66`).

### distllm (ramanathanlab/distllm, PyPI v1.0.2, MIT)
**What it is:** A research-grade, battle-used but lightly-tested HPC RAG engine with the working internals ragstack lacks.
**Useful:** LLMGenerator protocol + vLLM/LangChain(OpenAI+Anthropic+Gemini)/HF backends + `RagGenerator`; `name->(Config,Impl)` STRATEGIES factory + `BaseConfig` from_yaml/write_yaml; OpenAI-compatible `chat_server.py` with real SSE streaming; `FaissIndexV2` (flat/HNSW/binary, ubinary + rescore_multiplier); `semantic_chunk.py` (boundary-aware); `registry.py` singleton model cache; EvaluationTask/QA harness.
**Fills:** ragstack's #1/#2 gaps — **working LLM generation** and **multiple LLM backends** — plus scalable Faiss, semantic chunking, a RAG-quality eval harness, and config-driven reproducible runs.
**Overlap:** sibling wins on factory/config pattern; complementary on embedders, vector search, API surface; **ragstack wins on hybrid retrieval/RRF/cross-encoder (coded), engineering rigor, and conformance.**
**Verdict: INTEGRATE select components + BORROW patterns.** Integrate the generator protocol + RagGenerator (highest value). Borrow STRATEGIES/BaseConfig. Use-as-is `registry.py` and `semantic_chunk.py`. Reconcile its streaming shape into ragstack's contract — do NOT let its API replace ragstack's OpenAPI. Ignore protein/ESM encoders and Parsl/HPC layer. Caveat: lightly tested (no FaissIndexV2/Retriever/RagGenerator tests) and MCQA-specific prompts — add ragstack-side tests.

### ExaForge
**What it is:** A domain-orthogonal offline-batch HPC inference tool (~183 tests, respx-mocked, strict mypy; no CI, single language, no contract).
**Useful:** `EndpointPool` + `InferenceClient` (health-aware pool, global semaphore, round_robin/least_loaded, backoff retries, errors-as-data `ChatResponse`); `_extract_json` (qa_generation.py); `lustre.atomic_write`; `CheckpointManager` + two-phase `JsonlReader` (scan→filter_pending→read_by_ids) + streaming batch `Orchestrator`; `ItemSkipped` typed reject channel; discriminated-union-config-as-registry; QA-generation `BaseTask`.
**Fills:** working/resilient LLM client (multi-endpoint health + LB + retry + throttle); checkpoint/resume; memory-bounded streaming over arbitrary corpora; atomic/fsync I/O; synthetic eval-set generation; auditable skips.
**Overlap:** sibling wins on the inference client; complementary on config, pipeline orchestration, deployment; **ragstack wins on test discipline-in-CI, contract, cross-language conformance.**
**Verdict: BORROW + use two components as-is.** Lift `endpoints.py`+`client.py` as ragstack's resilient LLM/embedding transport; copy `_extract_json` and `atomic_write` verbatim. Adopt checkpoint + two-phase reader + `ItemSkipped` to make `IngestionPipeline` resumable/bounded/auditable. Files: `/rag/repos/ExaForge/src/exaforge/{client,endpoints,checkpoint,orchestrator,lustre,config}.py`, `readers/jsonl.py`, `tasks/qa_generation.py`. Do NOT run it as a component.

### rag_api
**What it is:** An early internal prototype (~1,200 LOC, no tests, no CI, wide-open CORS w/ credentials, committed plaintext API key, unbounded cache) — well behind ragstack on rigor.
**Useful:** working TF-IDF retrieval (Arrow vocab/idf, regex `\b\w\w+\b` tokenizer, faiss `IndexFlatIP`, no serve-time sklearn) in `rag_service.py`; MongoDB `ragList` corpus registry with one-name-to-many-configs fan-out + global re-rank; eager `preload_active_indexes()` returning loaded/skipped/failed; composite cache key; return query embedding in response; tri-state health.
**Fills:** working sparse/lexical retrieval *in the serving path*; a data-driven multi-corpus registry that *actually executes end-to-end* (vs ragstack's coded-but-unwired `HybridRetriever` and stub `list-documents`); HF-datasets document store.
**Overlap:** tie on retrieval-only-defer-generation; complementary on vector search and hybrid merge; **ragstack wins on embedding abstraction, contract, deployment, testing.**
**Verdict: BORROW concepts.** Port the TF-IDF encoder behind ragstack's `TextIndex` protocol; adopt registry + program-dispatch + eager-preload into ragstack's lifespan, backed by ragstack's *planned Postgres* (not Mongo). Low-effort grabs: preload summary, composite cache key, return-embedding, tri-state health. **Fix when borrowing the fan-out:** rag_api applies `top_k` per-config but never truncates the merged set to a global `top_k` (returns up to `N_configs * top_k`).

### GoWe (github.com/wilke/GoWe — a CWL v1.2 workflow engine)
**What it is:** Not a RAG component at all — zero functional overlap — but a strong *architectural* donor exactly where ragstack is weakest (orchestration, persistence, auth, Go maturity). 204 Go files, ~522 test funcs, CI tiers.
**Useful:** keyed `Executor` registry (4-method interface, 5 live backends); atomic capability/affinity `CheckoutTask` (`internal/store/sqlite.go:1783`); REST envelope w/ request_id/timestamp/pagination (`response.go`); SSE-over-polling (`handler_sse.go`); pure-Go SQLite `Store` + idempotent migrations + single-writer WAL; three-level declarative state machine w/ generic `canTransition` (`pkg/model/state.go`).
**Fills:** durable job/metadata persistence (ragstack's biggest unbuilt gap — `list-documents`/`ingest-status` stubs); async/distributed orchestration with retry/self-healing; broker-free pull-based workers (vs ragstack's planned Celery); working multi-provider auth + rate limiting (ragstack has CORS only); multi-scheme artifact staging (S3/HTTP corpus ingestion ragstack can't do).
**Overlap:** complementary on ports/adapters, API surface, deployment, domain; tie on conformance-driven development; **sibling wins on Go maturity and persistence/job state.**
**Verdict: BORROW patterns; do NOT depend on it, do NOT ignore.** Low-effort: Executor registry, state machine, SSE template. Medium: SQLite `Store` as ragstack's *Go-side* job/metadata store (swap to Postgres later behind the same interface); the GPU-vs-CPU embedding job routing maps almost exactly onto GoWe's `prestage=require`/`cache=prefer` scoring. Caveat to carry over: single-node SQLite (single writer, `max_open_conns=1`), no HA/multi-coordinator — matters more for ragstack's production-scale RAG than GoWe's niche.

## Cross-cutting themes

**1. The same two gaps recur everywhere: generation and orchestration.** Four of five siblings either have or directly address ragstack's `[LLM not yet wired]` gap (distllm and ExaForge with *working code*; GoWe with the orchestration to run it; rag_api deliberately defers it). This is the strongest signal in the set: **wire an LLM client now.** distllm gives the RAG-specific generator + backends; ExaForge gives the resilient transport. Use both.

**2. "Config-as-registry" is a unanimous architectural recommendation.** distllm (STRATEGIES + discriminated unions), ExaForge (`Field(discriminator='name')`), and GoWe (keyed Executor registry) independently converge on: *one declarative `name` field both validates a sub-config and selects an implementation.* ragstack already has the seams (`protocols.py`) but selects backends imperatively in `deps.py` with import-guard fallbacks. This is the highest-leverage low-effort refactor — it makes `config.py`'s enumerated-but-unused backends (Qdrant/ES/Neo4j/Postgres/Redis) actually selectable and makes runs reproducible.

**3. ragstack's real sparse retrieval is a placeholder, and two siblings fix it cheaply.** `InMemoryTextIndex` is Jaccard, not BM25; Elasticsearch is unbuilt. Both rag_api and embedding_app ship working TF-IDF over faiss `IndexFlatIP`. TF-IDF ≠ BM25, so this is a *credible stopgap behind the `TextIndex` protocol*, not the ES endgame — but it turns coded-but-unwired hybrid retrieval into something that executes.

**4. ragstack leads the set on rigor; that lead is its moat — protect it.** Every sibling is weaker on testing-in-CI, API contract, and cross-language conformance (ExaForge and GoWe have strong tests but no contract/conformance; rag_api and embedding_app have effectively none). The recurring instruction is identical across all five: *borrow parts, never integrate wholesale, never replace the OpenAPI contract or run the conformance suite against a sibling.* Any lifted code needs ragstack-side tests before it counts as production.

**5. ragstack's persistence and async story is entirely unbuilt — and it's the gating dependency for everything else.** `list-documents`/`ingest-status` stubs, no job table, synchronous in-process ingestion, planned-only Celery/Redis/Postgres. Resumability (ExaForge checkpoints), durable state (GoWe SQLite Store), and distributed dispatch (GoWe CheckoutTask) all hinge on this. Until there's a metadata/job store, the stub endpoints can't become real and large-corpus ingestion stays one-shot and unbounded.

**6. ragstack already wins where the siblings are thin: hybrid retrieval.** `HybridRetriever` (vector+BM25+graph via RRF) and `CrossEncoderScorer` are *coded* — distllm/rag_api/embedding_app have at most single-modality or naive-score-sort merging. ragstack's job here is *wiring*, not building. The knowledge graph remains a true gap for the whole set (only ragstack even plans it; no sibling has one).

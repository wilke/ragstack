The front door

Front proxy

One rootless nginx on :9000 / :9443 fronts every service on this host, so external callers get one host, one port and one CORS policy instead of a dozen bare uvicorn and vLLM ports. Prefer it over the bare ports for anything outside the machine.

This page is not the authority on the proxy. Routing tables, CORS, TLS, the rootless Apptainer constraints, log rotation and its own gotcha list live in coconut front proxy. Deliberately not duplicated here — two copies of a routing table drift, and the drifted one is always the one someone reads at 2am.

CORRECTION — a bearer identity CAN now be an admin. This page previously said a bearer identity was hardcoded to user and could never be admin, and that “an admin is always an API key.” That stopped being true on 2026-08-06. Anyone who planned around the old sentence should re-read Tenancy.

The hardcoding was deliberate, and so is its removal. Production sets DEFAULT_ROLE=admin, so letting a bearer identity fall through to the default would have made every authenticated user a superuser. A bearer identity is now admin only when an explicit server-side source names it: the ADMIN_SUBJECTS env allowlist, or a stored users.role written through PATCH /v1/admin/users/{subject}/role. Nothing that travels with the credential is an input, so a token cannot elevate itself, and the store read fails closed — an outage withholds admin rather than granting it.

Every non-production API requires a credential. Each has an admin key and a user key; DEFAULT_ROLE is user there, so an unmapped caller is never an admin. Keys are mode-600 files under /rag/data/migration-2026-08-05/, alongside the migration playbook and the rollback snapshots.

A bearer admin reaches every /v1/admin/* route, including service-account registration — require_role tests the principal's role, not which credential produced it. There is also no “disable this person” lever: the disabled-account gate runs only on the API-key path. Stopping a bearer admin means revoking the stored role (bounded by the role-cache TTL, per worker), an env edit plus restart, or revoking the identity at its issuer.

Each migrated tenant has its own ACL database (users, shares, groups, group_members) under its own state directory — per ADR-0005 the schema is shared, the instance is not. Back it up with the stores: a lost ACL database means orphaned collections nothing can reach.

The demo's BM25 was in memory until 2026-08-05 and is gone; its vectors survive in Qdrant, so the text side can be rebuilt from payloads. TEXT_BACKEND is now elasticsearch there.

How collections are separated in Elasticsearch

One index per collection. A collection's ES index name rides on its physical collection name (CollectionSpec.es_index), so each corpus gets its own index — lucid_sfr_tok256, ragstack_sfr_tok256, demo_g1_sfr_tok512 and so on. Inside an index, the boundary is a tenant_id filter, and it is enforced rather than advisory: search refuses a query whose tenant_id filter is empty instead of defaulting to everything.

This is why the one-entry-per-store rule compares both legs. Two registry ids sharing an ES index are the same two-ACLs-over-one-dataset defect as sharing a Qdrant collection; a hand-authored spec could arrange exactly that until 2026-08-06.

Index separation is not process separation. Every index above lives in one Elasticsearch on :9200, shared by both production tenants. An index name is a value in a request, not a boundary anything enforces below the application — and this ES has no authentication. Anything that can reach :9200 can read any index. dev is the only deployment whose text leg is its own process.

What :8020 taught us, and why it is gone. The “Unified Explorer” pointed at ASM's Qdrant, ASM's ES index and the shared manifest directory. So it listed ASM's collections — which is how this was noticed — but the real problem was the other direction: it was a writable API over production data, sitting outside the read-only guard that protects the asm route. The guard locked the front door while this was an unlocked side door into the same room. It was stopped on 2026-08-06 and nothing routes to it.

The general lesson is worth more than the incident: a read-only guard on a route is only as good as the set of routes that reach the store. Before trusting one, enumerate every process that can write to the data, not every path that is guarded.

Provisioning a tenant

apptainer/new-tenant.sh <name> --start creates the per-tenant directory tree, a dedicated Qdrant and Elasticsearch, a generated tenant.env, and bin/up.sh / bin/down.sh. It is idempotent, and --dry-run touches nothing.

Port allocation needs an explicit base today. The allocator's manifest ($RAG_DATA/tenants/manifest.tsv) does not exist on this host: the lucid and asm tenant directories were created before it, so the script has no record of 24000/24020. It probes live ports and refuses rather than allocating a colliding block — good — but that means every new tenant needs TENANT_PORT_BASE=<free base> until those two are reconciled into a manifest. dev was provisioned at 24040 this way.

A fresh tenant is not empty-looking. It boots with one collection named default, whose label is a derived physical store name (ragstack_<model>_<dim>_<hash>) with count: 0. Two things combine: the served collection name is content-addressed from the build spec, and the API creates that Qdrant collection eagerly at startup so the first request cannot race. Because the name is deterministic, the same build spec yields the same name on every instance — identical names on two Qdrants are not shared data.

Exclusive ownership by ADOPTION — ADR-0005 decision 7

The asm tenant's stores are the existing Qdrant :6333 and Elasticsearch :9200 — not the empty per-tenant instances the provisioning script stamped out (/rag/data/tenants/asm/{qdrant,elasticsearch} are 12K and 16K placeholders, and stay dormant). ADR-0005's boundary test is data at rest, and the data at rest on those instances is asm's: three corpora, 40.4M points, 58 GB of text index. Standing up fresh stores would have meant moving all of it to satisfy a naming convention.

Adoption inverts the cost. The data stays; what remains is a decommission list of co-tenants, each with a defined exit. The store inventory is the progress meter — adoption is COMPLETE when every store on these instances shows exactly one owner:

The open-access corpus and its ingest plane

A second corpus is being ingested into the asm tenant: PubMed Central open access, 1.44M JATS XML articles harvested to /rag/oa/corpus (191 GB, hash-fanned, 0 missing / 0 hash mismatches at verify). It becomes the second-largest collection on :6333.

StageToolNotes
0 · registerPOST /v1/collectionsfirst, not last — a bulk writer refuses a --collection-id the registry does not hold (#263). The physical name is server-minted.
1 · excludescan_notices.pyretraction is a SEPARATE article naming its target, so exclusion is two-hop: notice + the retracted original. 33,154 excluded of 1.44M.
2 · planplan_shards.pyshard = sha1(pmcid) % N — re-planning a growing corpus moves nothing. 2,048 shards, CV 4.3%.
3 · rungowe_batch_ingest.py64-shard batches: submit → verify both legs → reclaim ~82 GB → next. Resumable ledger; re-attaches on timeout.
4 · per batchjats-ingest.cwltwo TOP-LEVEL scatters (extract-all → embed-all), then one load. ~6.0 h/batch measured.

Never scatter over a sub-workflow on this GoWe. The chained scatter(extract → embed) shape is prettier dataflow and it cost a day: dispatchScatterSubWorkflow executes children strictly serially, inline in the scheduler loop, so it runs at 1/N speed, blocks every other submission on the engine for its duration, and cannot be stopped — cancelling the parent is ignored between iterations and a cancelled child finalizes in a state the loop reads as success. Only a server restart stops it. Handoff spec with a self-contained reproducer: GoWe#164. Use flat top-level scatters.

Qdrant needs a doc_id payload index. index_chunks delete-priors per document; unindexed, every delete is a full collection scan — a load past ~150k points ground to ~1 delete/s and looked like a network hang. Creating the index live took the same load to ~125/s. ensure_collection now creates it and back-fills existing collections at boot (#307).

Payload shape differs per leg. Qdrant payloads are FLAT (content_type); Elasticsearch nests under metadata.* (metadata.content_type). A filter that works on one leg silently matches nothing on the other. The JATS records carry content_type = article | table | figure, which is what makes “filter to data tables” answerable — it survives to the chunk payload only because JsonlLoader gained an opt-in metadata pass-through.

Fixed 2026-08-06 · #275

A physical index has exactly one registry entry

Access control is asserted at the collection (ADR-0003). So two registry ids over one physical store are two independent ACLs over one dataset: revoking a grant on one id leaves the same bytes readable through the other. An owner who un-publishes a corpus has not un-published it.

The registry used to synthesise an entry called default from the top-level settings and then append every configured spec. Where a spec named the same store — the ordinary shape for QDRANT_COLLECTION_EXPLICIT plus a matching spec — the same corpus was served under two ids. That was live on lucid-next, and the 21-second window in which one id was un-published while the other still served the same 1.5M-point corpus is in that tenant's share audit trail.

What changed. The derived entry is created only when no spec claims its store; two specs may not claim one store; a spec claiming only one of the two legs is a startup error rather than a silent suppression (suppressing left the other store served by no entry, hence governed by no ACL); and default is a reserved, uncreatable id naming the pointer (DEFAULT_COLLECTION_ID).

“Is the default” and “is the legacy shared surface” are different questions. They used to be one flag, because the pointer could only ever name the settings-derived entry. The surface carries two authz exemptions — no share-based scope widening, and read-not-write on the omitted-collection ingest and document-delete paths — because there per-chunk tenant_id is the isolation. Letting those follow the pointer would let any reader of an owned collection write to it by omitting collection. Separate flags now; see ADR-0002 decision 5.

Upgrade consequence, observed on lucid-next. After restart the id default ceases to exist there: a request naming it explicitly 404s, and its two ACL rows (lucid owner, public read) are left orphaned and active. They are inert — nothing reads them — but they mean any revocation an operator recorded against default is silently discarded, and the reverse: a corpus un-published on default alone is now published. Reconciling them is the migration script (#276), which needs ownership transfer (#280) first.

Who you are

Signing in

The UI has a sign-in page with a provider dropdown, and the header shows the identity the server reported — never a name read out of the pasted token.

ProviderHowState
BV-BRCusername + password, or paste a p3-login tokenworking
API keya configured key — a tenant, not a personworking
Google / OIDCauthorization code + PKCE redirectlisted, disabled — browser half not built
MG-RAST—absent: no password exchange upstream, and no provider to verify its token here

The password never reaches RAGStack. The browser posts it straight to user.patricbrc.org/authenticate and receives the same signed token p3-login writes. That is possible because BV-BRC echoes the caller's Origin and its preflight allows the POST. A server-side pass-through would have been easier and strictly worse — it would put user passwords through a service with no business holding them and make the request logs credential-bearing. The API has no endpoint that accepts a password and must never gain one.

The token is stored in localStorage bound to the backend it was confirmed for, and that binding is enforced when each request's header is built, not in UI state. A BV-BRC token has no audience claim and cannot be revoked before it expires, so sending it to a backend the user never confirmed would hand over their whole BV-BRC session.

Password sign-in requires HTTPS, and today that means a self-signed cert. On a plaintext page an on-path attacker can rewrite the form before it renders — posting to the provider over TLS is no defence when the attacker replaced the code doing the posting. The UI therefore refuses to reassure on an insecure origin: it shows a red warning and points at the token paste instead. http://localhost:9000 is fine (browsers treat localhost as secure); http://coconut.cels.anl.gov:9000 is not. :9443 works but its certificate is self-signed, and training people to click through a certificate warning before typing a password is its own bad habit. A real certificate is what makes this feature safe to use.

Bearer sign-in only works where IDENTITY_PROVIDER is set. It is on for demo and dev; on lucid-next and asm-next it is unset, so the Authorization header is not an authentication input at all and a token request 401s. That is the usual cause of “I signed in and it says I'm not signed in.”

Migration safety

The gateway refuses writes to asm and lucid

While the production tenants are being migrated, the front proxy returns 403 to API calls that would mutate them — before authentication, so it does not depend on the app being correct.

Requestasm / lucideverything else
POST /v1/query · /v1/retrieve200200
POST /v1/ingest403allowed
POST/PUT/PATCH/DELETE /v1/collections403allowed
PUT/PATCH/DELETE /v1/documents403allowed
POST/PUT/PATCH/DELETE /v1/admin · /v1/jobs403allowed

Path-based, not method-based — and that distinction is the whole design. POST /v1/query and POST /v1/retrieve are reads that happen to be POSTs. A method-based rule would have returned 403 for both and taken every consuming service offline. The map matches method and path, and query/retrieve are deliberately absent from it.

What this does not cover. It is a gateway guard, not authorization. The API ports still bind 0.0.0.0, so anything on the host can bypass it entirely; and the bulk ingest CLI writes to Qdrant directly, never touching the API. Binding those ports to localhost is a production restart and belongs in the cutover window.

The embedding model is immutable per collection. A collection's identity is (model, dim, chunker). You cannot re-point an existing collection at a different embedder — the stored vectors would be incomparable. Changing it means a new collection and a full re-ingest. As of the latest build the API enforces this with a 409 rather than silently appending incoherent data.

Configuration

Files and precedence

Config is environment variables. Files under /rag/config/ are sourced into the shell before launch — they are not read by the app directly.

lucid.env contains live API keys. Mode is 0644. Treat the file as a secret; do not copy it into tickets, logs, or repos.

Sourcing gotcha: use set -a; . file; set +a. Do not pipe through xargs — values containing JSON or spaces are mangled. And EMBEDDING_ENDPOINTS must be a comma list, not a JSON array: shell sourcing strips the quotes and the app then rejects it.

Operations

Starting and stopping

Stopping — by PID, never by pattern

A pkill -f "port 8030" matches the shell running it and kills your own session. This has happened repeatedly. Always resolve the PID first:

# find it
ss -lntp | grep ':8030 '
# stop it (SIGTERM; uvicorn drains)
kill <pid>

Restarting a production API

Capture the running environment first — :8000 in particular has no config file, so its settings exist only in the running process:

tr '\0' '\n' < /proc/<pid>/environ | grep -E '^(QDRANT_|ELASTICSEARCH_|EMBEDDING_|CHUNK_|LLM_|INGEST_ROOT|DEFAULT_ROLE)='
readlink /proc/<pid>/cwd

Then relaunch from the same working directory with the same variables. For file-configured servers:

cd /rag/repos/ragstack/python
set -a; . /rag/config/lucid.env; set +a
export HF_HOME=/rag/cache
nohup /rag/envs/ragstack/bin/uvicorn ragstack.api.main:app \
      --host 0.0.0.0 --port 8010 >> /rag/config/lucid.uvicorn.log 2>&1 &

Verifying after a restart

curl -s localhost:8010/health                 # {"status":"ok"}
curl -s localhost:8010/v1/stats/stores        # counts must match pre-restart
curl -s localhost:8010/v1/collections | jq '.collections[]|{id,count}'

Python environment: /rag/envs/ragstack. It holds an editable install pinned to /rag/repos/ragstack/python, so the production servers import from that checkout regardless of your shell's cwd. The demo servers override this with PYTHONPATH.

The production checkout is not on main. /rag/repos/ragstack sits on a feature branch, ahead of main with unmerged ingest work and well behind it otherwise. A naive git checkout main there discards that work. A tagged pre-change commit exists as a revert anchor; see the restore runbook in docs/production-restore.md before updating either prod server.

OpenAPI 3.1 source of truth: contracts/openapi.yaml. Live docs at /docs on any server. Auth is X-API-Key where keys are configured; bearer-token identity (BV-BRC / OIDC) exists behind a flag and is off by default.

Common calls

# ask a question, grounded, with citations
curl -s localhost:8030/v1/query -H 'Content-Type: application/json' \
  -d '{"query":"...","collection":"open-access","top_k":5}'

# upload PDFs → returns a job_id; poll it
curl -s -X POST localhost:8030/v1/ingest/upload \
  -F 'files=@paper.pdf;type=application/pdf' -F 'collection=open-access'
curl -s localhost:8030/v1/ingest/<job_id>

# what is actually indexed, and is it in parity
curl -s localhost:8030/v1/collections | jq '.collections[]|{id,count,text_count}'

Ingest paths. Three exist and are documented in docs/ingest-paths.md: the local API path above (what the demo uses); a GoWe/CWL path for scaled batch work (INGEST_BACKEND=gowe, consumes pre-extracted JSONL shards); and a bulk CLI (scripts/ingest_jsonl.py) for operator corpus builds. A job_id from the local path lives in RAGStack's job store and will not appear in GoWe.

Read before touching anything

Operational cautions

Things that have already gone wrong here

  • Killing by pattern. pkill -f "port 80xx" matches the invoking shell. Use PIDs.
  • VMA exhaustion. A bulk rebuild exhausted vm.max_map_count and took Qdrant down. The limit was raised to 262,144; leave optimizer thread caps alone during bulk work.
  • Elasticsearch client major. The 9.x Python client is rejected by an 8.x server at runtime, not install time. The dependency is now pinned <9 — don't loosen it while the servers are 8.x.
  • Silent index drift. A collection's Qdrant and ES counts should match. A gap means one leg missed writes; the Ops UI shows a parity badge for this.
  • Orphaned stores. Deleting a collection historically dropped only the registry binding, leaving vectors on disk. ?purge=true now removes the data; without it, expect orphans.
  • A “safe” probe that wasn't. POST /v1/collections with an empty body {} was assumed to be an invalid request that would 422. It is valid — open collection creation fills in the server-default build spec — so it returned 201 and created a registry entry, a Qdrant collection and an ES index on the production instance. All empty, and left in place for the migration. Read-only intent is not read-only behaviour: on a stack that shares production stores, verify a guard by reading the config, not by sending the write.
  • A guarded route is not a guarded store. The gateway's read-only guard covered asm and lucid while :8020 wrote to the same Qdrant and ES from an unguarded route. Enumerate every process that can reach the data, not every path that is guarded.
  • “I signed in and it says I'm not signed in.” Almost always IDENTITY_PROVIDER unset on that backend: the Authorization header is then not an authentication input at all, the request 401s, and the UI reports the truth. Check the backend before suspecting the login code.

Known gaps

  • No real TLS certificate. :9443 is self-signed. This now blocks a feature rather than merely being untidy: password sign-in is refused on an insecure origin, and the alternative — teaching people to click through a certificate warning before typing a password — is worse than not having it. Highest-value gap on this list after backups.
  • The tenant port manifest does not exist. $RAG_DATA/tenants/manifest.tsv is missing, so new-tenant.sh cannot see the blocks lucid-next and asm-next occupy. It fails safe (probes live ports and refuses), but every new tenant needs an explicit TENANT_PORT_BASE until those two are reconciled.
  • No collection management beyond create / share / delete — no rename, no ownership transfer (the API tells callers to "use the transfer flow"; there isn't one, #280), no way to repoint the default without an env edit and a restart, and no merge tooling for the orphaned ACL rows above. These interlock: the collection default points at cannot be deleted, and repointing needs a restart, so a user whose collection became the default has no in-API way out (#281).
  • No tenant inventory or drift check. Nothing enumerates provisioned tenants and their store bindings, and nothing verifies a tenant's tenant.env still describes what is running. Two live examples today: a tenant directory pointing at production stores rather than its own, and an API that ran for hours with its identity provider set only as a runtime override, absent from its config file (#281).
  • Elasticsearch is still shared by everything except dev, including both production tenants. Qdrant is separated for Lucid; ES is not. A per-tenant ES is what new-tenant.sh now produces, so the path is known — it just has not been walked for asm and lucid.
  • API ports bind 0.0.0.0. The gateway's read-only guard can be bypassed by anything on the host, and the bulk ingest CLI writes to Qdrant without touching the API at all. Binding to localhost is a production restart.
  • USER_STORE_BACKEND defaults to memory in config.py (only .env.example says sqlite). With memory, every role grant vanishes on restart and each worker keeps its own table — which matters more now that an admin role lives in that table. ADR-0004 targets Postgres; the live tenants run sqlite, whose single-writer guarantees hold only within one file on one host.
  • No metrics endpoint. No /metrics, no OTEL. Observability is logs plus the Ops page.
  • Single worker. The API runs one uvicorn worker. Several in-process caches and registries assume that; raising --workers needs work first.
  • No OCR. Scanned PDFs fail ingest with a clear error rather than being processed.
  • GoWe worker hygiene. Task directories are never cleaned up and accumulate tens of GB. Cron a find … -mtime +7 -delete.
  • GoWe authentication needs hardening before any wider network exposure. Details were reported separately and privately; treat the engine as trusted-network-only until then.
  • The published docs are stale. wilke.github.io/ragstack/architecture.html is generated from docs/ARCHITECTURE.md and last built 2026-07-02. It describes the repo's intended stack — BGE 768-d, one API server, Neo4j, Docker Compose — none of which matches this deployment. This page supersedes it for anything operational.

Backups

There is no automated backup of Qdrant or Elasticsearch today. The corpora are re-derivable from source documents plus the recorded build spec, but a rebuild is a multi-day GPU job. Snapshot policy is the highest-value operational gap on this list.

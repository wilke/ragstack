## Setup

- **Corpus subset:** 1500 `article`-class records (non-empty title), sampled
  deterministically (seed 0) **balanced across the 3 input files**
  (09320c55-a8a, 0a4f7390-da1, 0d1bb3c8-ecf). The *same* subset feeds
  all 7 configs.
- **Eval queries:** 1000 known-item queries (query = doc title, relevant = its
  own doc_id), deterministic sample (seed 0), top_k=10, rerank pool
  50. Same query set across all configs.
- **Embedding fleet:** 16 live SFR endpoint(s) used round-robin
  — 8 on coconut (`:9001-9008`, keyless) + 8 on lambda13
  (`:9990-9997`, keyed). GPU load is spread by round-robin batch assignment across
  the live pool; semantic's per-doc buffer embeds also fan across the pool.
- **Retrieval:** `HybridRetriever` (Qdrant dense + ES BM25, RRF fusion), tenant
  `public`, isolated `chunkcmp_m7_<config>` stores. Reranked pass pulls a
  50-candidate pool, reranks with the crossencoder sidecar (`:50052`).
- **Token safety:** every config is hard-capped at 4080 tokens; the
  `overflow>4080` column counts chunks that exceeded it and were split.

## Findings

**(a) Does the char-vs-token *unit* matter once size is matched?** `fixed_char2048` (median 681 tok) vs `fixed_tok512` (median 513 tok): reranked recall@5 0.900 vs 0.902 (hybrid recall@5 0.905 vs 0.897). A small delta means the *unit* is second-order once the effective size matches; the token window's value is determinism/safety, not raw quality.

**(b) Does chunk *size* matter?** `fixed_tok256` vs `fixed_tok512`: reranked recall@5 0.905 vs 0.902, chunks/doc 72.0 vs 36.2. Smaller windows cost ~2x the chunks (and embed/store); the quality delta tells you whether that buys anything for title-known-item retrieval.

**(c) Does any method beat the cheap fixed baseline at full token-safety?** Baseline `fixed_char512` reranked recall@5 0.902. Best token-safe config `fixed_tok256` = 0.905 (delta +0.003). Every non-baseline config is token-capped at 4080 so none can overflow the SFR window.

**(d) Per-config token-overflow (chunks that exceeded 4080 tokens and had to be split):** fixed_char512=0, fixed_char2048=0, fixed_tok256=0, fixed_tok512=0, sentence_tok512=0, words_tok512=0, semantic_tokcap=0. This is the token-safety payoff: the char configs and semantic are where un-capped chunking would have sent over-window text to the embedder; the token-sized configs never overflow by construction.

## Recommendation

**Quality winner: `fixed_tok256`** (reranked recall@5 0.905, hybrid MRR@10 0.890), median 257 tok / 72.0 chunks/doc, 0 overflow. **Cheapest: `fixed_char2048`** (210s). For a full prod rebuild, weigh the quality winner against `fixed_tok512` — a fully token-safe, deterministic 512-token window that matches the prod corpus' effective size while guaranteeing zero embedder overflow.

## Caveats

- **Title-query proxy.** Known-item-by-title flatters lexical/BM25 matching (the
  title's words often appear verbatim in the lead chunk). Read hybrid and reranked
  columns together.
- **Single relevant doc.** recall/MRR/nDCG assume exactly one relevant document per
  query (the source).
- **Subset, not the full corpus.** 1500 docs across 3 files; absolute numbers
  would shift on the full 877k-chunk corpus, but the *relative* config ordering is
  the signal.

# User-bound programmatic API keys (#584) — implementation plan

**Status:** `PLANNED`, not started. Written 2026-09-17. Reviewed by Fable before any code.
**Issue:** [#584](https://github.com/wilke/ragstack/issues/584)

---

## 0. Why this is not speculative

Measured 2026-09-17 with `ragstack.ops.tenant_keys`, which reports a sha256
prefix and never a value:

| tenant | file | keys | `user` | `admin` | other |
|---|---|---:|---:|---:|---|
| asm | `tenant.env` | 33 | **31** | 1 | 1 default |
| hackathon | **`secrets.env`** | 32 | **31** | 1 | |
| lucid | `tenant.env` | 3 | 1 | 1 | 1 `researcher` |
| dev | `tenant.env` | 2 | 1 | 1 | |
| demo | `tenant.env` | 2 | 0 | 1 | 1 default |
| **total** | | **72** | **64** | **5** | |

**64 of 72 keys are already user-role**, and on asm **30 of them authenticate as
the single subject `asm-ro`** — thirty people sharing one identity, so none of
them can own a collection, shares cannot distinguish them, and revoking one
revokes all thirty. The env-file service-account mechanism is already being used
as a user-key system; this feature does not introduce the use case, it gives an
existing one a correct shape. Each of those 64 costs an operator edit plus an API
restart to issue, and the same to revoke.

> Hackathon's ledger is in `secrets.env` (the `env normalize` layout), not
> `tenant.env`. The argument is stronger than first written, and "flip on
> hackathon first" was reasoned from a wrong number — see §5 step 10.

Reserved-prefix collisions (`rsk_`) across all five tenants: **0**, so §2.3 costs
nothing today.

## 1. What is being added

A credential a user mints for themselves that authenticates **as their own
subject**, so authorization is entirely unchanged: same ownership, same shares,
same groups, same quotas.

```
POST   /v1/me/keys           {label, scope, expires_in_days?}  -> value ONCE + metadata
GET    /v1/me/keys           metadata only, never values
DELETE /v1/me/keys/{id}
GET    /v1/admin/users/{subject}/keys
DELETE /v1/admin/users/{subject}/keys/{id}
```

### What is NOT being added

* Nothing moves the existing env-file keys. Their path stays byte-identical —
  this is the single hardest acceptance criterion and the first test to write.
* No ctl involvement. The control plane never sees a user credential.
* No UI. A "My API keys" panel is the UI session's call once the API exists.

## 2. The decisions that close the gaps found in two rounds of review

### 2.1 Scope is declared per route — but the keystone has to be built first

**Not** by HTTP method: `/v1/query` and `/v1/retrieve` are POSTs that do not
write, so a method heuristic needs an exception list on day one — the shape that
produced #471, one rule with two interpreters diverging silently.

Key scope on the OpenAPI **`operationId`**, so the contract and the enforcement
cannot drift. **The review found this does not work yet.** The contract declares
an `operationId` on all 62 operations, but **zero Python routes set one**
(`grep -rn operation_id python/ragstack/api/` → 0). The served ids are
FastAPI's autogenerated `retrieve_v1_retrieve_post`; **0 of 62 match the
contract's `retrieve`**. An allowlist keyed on contract ids would therefore
enforce nothing, and the "subset of declared operationIds" test would pass while
doing so.

So step 0 is: **set `operation_id="<contract id>"` on all 62 routes, with a test
asserting served ids == contract ids.** That is independently valuable — it is a
real contract/implementation gap — and it is landable before any of this feature.

Once ids are set, a single router-level dependency can read
`request.scope["route"].operation_id` (verified on this FastAPI 0.138.0 /
Starlette 1.3.1), so enforcement is one dependency, not per router.

```python
# ragstack/api/scopes.py  (new)
#: Operations a `read` key may reach. ABSENCE IS THE DEFAULT AND MEANS REFUSED,
#: so a route added without thought is unreachable, never accidentally readable.
READ_SCOPED: frozenset[str] = frozenset({
    "query", "retrieve", "getChunks", "listCollections", "versionInfo",
    "listDocuments", "statsTenants", "listEntities", "getNeighbors",
    "graphStats", "listPromptTemplates", "listAvailableModels",
    "listCollectionShares", "listGroups", "getGroup", "ingestStatus", ...
})
```

> Corrected from the first draft, which invented `get_collection`,
> `get_document` and `me` (none exist) and misspelled `getChunks` and
> `versionInfo`. **`/v1/me` does not exist at all** — `stats.py:243-247` says so
> explicitly; whoami is `GET /v1/stats/tenants?counts=false`, which the UI calls
> on every credential change and which therefore must be read-scoped.

### 2.2 Scope is a ceiling applied after role resolution

Role comes from **`_bearer_role`** (`security.py:638-654`) — `ADMIN_SUBJECTS`, then
the stored role, failing closed to `user`. Never `DEFAULT_ROLE`, never
`API_KEY_ROLES`: a user key is a bearer identity wearing a key, and
`access.py:555-583 _subject_is_admin` already routes bearer-shaped subjects the
same way, so ownership caps stay consistent. Add a test that a user key never
consults `settings.default_role`. Scope then narrows whatever that returns.
Otherwise an admin's "read-only key for a script" is a read-only key to the whole
tenant — every other user's collections, `/v1/config`, the admin listings.

```
effective = role_from_usual_sources(subject)
if scope == READ and operation not in READ_SCOPED:  -> 403, naming the scope
if scope == READ and operation is an ADMIN operation: -> 403   # admin is opt-in
```

A third scope `admin` may be minted **only** by a subject that already has the
admin role, and is the only way a key exercises admin surfaces. Default on mint is
`read`.

### 2.2b A user key cannot submit a workflow — and that limits what `full` means

**The largest finding of the review, and it narrows the feature.**

`gowe_caller` (`security.py:904-919`) returns a submission identity only when
`principal.token` is set *and* `principal.issuer == "bvbrc"`. A user-key
principal has neither: the key is not a BV-BRC token, and storing one to delegate
is precisely what this feature exists to avoid. Its docstring forbids a fallback
identity, and that rule is right — the engine stages `ws://` paths under the
caller's own Workspace home.

So on a `gowe`-backed tenant a user key cannot reach:

| route | refusal today |
|---|---|
| `POST /v1/ingest`, `/v1/ingest/upload` | 401 (`routers/documents.py:473-491`) |
| `POST /v1/collections/{id}/restore` | 400 (`routers/collections.py:881-888`) |
| `POST /v1/collections/{id}/graph` | 401 (`:1026-1033`) |
| the lifecycle auto-restore gate | 503 (`lifecycle.py:232-240`) |

The last one is not an ingest route: `access.py:49` runs `enforce_lifecycle` on
**every ACL-checked read**, so a *read*-scoped key querying a dormant collection
cannot wake it either.

`INGEST_BACKEND=gowe` on **dev** and **hackathon**; asm, lucid and demo are
`local` (unset), where ingest does not need a Workspace identity.

Consequences for this plan:

1. **Rename the scope.** `full` promises something it cannot deliver on the two
   gowe tenants. Use `write` (everything a key *can* do) and document the gap, or
   keep `full` only if the docs say plainly what it excludes.
2. **The refusals must name the credential class**, not just the missing token:
   *"a user API key cannot submit a workflow — use your BV-BRC token for ingest"*.
   Today they say a user token is required, which reads as a bug to someone
   holding a key they were told is `full`.
3. **Acceptance must not be proved on hackathon alone** (§5 step 10): it is
   gowe-backed, so it proves query/retrieve/share and *cannot* prove ingest.

This is not a reason to drop the feature — 64 existing keys are read-shaped, and
`asm-ro` is literally named for it — but the issue's framing ("script against
their own libraries") includes uploading, and on hackathon it will not.

### 2.3 The prefix is reserved, and startup refuses a collision

Dispatch is on the `rsk_` prefix, so an env key beginning with `rsk_` would be
looked up in the user store, miss, and then either fall through (a timing oracle
for "is this a live user key") or 401 (silently breaking an operator key).

Validate at startup: **no `API_KEYS` entry may begin with `rsk_`; refuse to boot
if one does.** Measured 2026-09-17: zero collisions across all five tenants, so
this costs nothing today and makes the dispatch total. Same check in the ctl's
`key mint`.

### 2.4 Fail closed — deliberately unlike its neighbour

`_service_account_disabled` fails **open** on purpose (`security.py:49`, `:573`
call the asymmetry intentional): a store error must not break an
already-verified identity. For a user key the store **is** the identity, so an
unanswerable store means *no authentication*, not a benign one. A user key whose
lookup errors gets **503**, never a principal.

This must be commented at both sites or a future reader will harmonise them the
wrong way.

## 3. Storage

The tenant's existing user store. `UserRecord.kind` already splits `human` from
`service` (#258); a user key binds to a **`human`** row.

```sql
CREATE TABLE user_api_keys (
  id           TEXT PRIMARY KEY,      -- 'uk_' + 16 hex, safe to log
  subject      TEXT NOT NULL,         -- FK -> users.subject, the bound identity
  key_hash     TEXT NOT NULL UNIQUE,  -- sha256 of the value; 256-bit random, so no KDF needed
  fingerprint  TEXT NOT NULL,         -- first 8 of the hash, for support ("which key is this?")
  label        TEXT NOT NULL,
  scope        TEXT NOT NULL,         -- read | full | admin
  created_at   TEXT NOT NULL,
  expires_at   TEXT,                  -- NULL = no expiry
  last_used_at TEXT,                  -- coarse (>=60s granularity), for offboarding review
  revoked_at   TEXT
);
CREATE INDEX user_api_keys_subject ON user_api_keys (subject);
```

Backends: sqlite and postgres (all five live tenants are one or the other —
hackathon postgres, the rest sqlite). **The memory backend must implement the
methods too** — unit tests run on it — with the refusal decided by a config
check, not by a missing method.

**Migration is a second DDL statement**, not new machinery: follow
`SqliteUserStore.__init__` / `PostgresUserStore._pool_` under the existing
`_USERS_DDL_LOCK_KEY` pattern (`user_store.py:785-825`). There is no FK
convention in this schema (shares has none, sqlite FKs are off by default) —
do not introduce one. `ensure_columns_*` is the only migration tooling and the
Alembic gap is repo-wide debt, not this feature's to pay.

**Mint must `await ensure_provisional(subject, issuer)` first.** The bearer
profile upsert is fire-and-forget and debounced (`user_store.py:753`), so the
`human` row is not guaranteed to exist at mint time.

**`memory` is the config default (`config.py:807`).** Minting there produces a
credential that silently dies at restart, so **mint refuses on a non-durable
backend** with a 501 naming it. This is the failure that would otherwise be
discovered by a user whose script stops working for no visible reason.

### Protocol additions (`user_store.py`)

```python
async def create_api_key(self, subject, *, id, key_hash, fingerprint,
                         label, scope, expires_at) -> UserApiKey: ...
async def get_api_key_by_hash(self, key_hash) -> UserApiKey | None: ...   # hot path
async def list_api_keys(self, subject) -> list[UserApiKey]: ...           # never values
async def revoke_api_key(self, subject, id) -> bool: ...
async def revoke_all_api_keys(self, subject) -> int: ...                  # offboarding
async def touch_api_key(self, id) -> None: ...                            # last_used_at, best-effort
```

**There is no offboarding hook to hang this on — one must be chosen.** The first
draft said `revoke_all_api_keys` is called by `admin remove`/disable. Review
found neither exists: there is no user-removal route anywhere, the only
`admin_users` route is `PATCH /users/{subject}/role` (`admin_users.py:184`), and
disabling a `human` row is refused by design (`:53-61`). So the promised test
cannot be written today. Pick one, explicitly:

* **`DELETE /v1/admin/users/{subject}/keys`** — revoke-all as the offboarding
  lever, admin-only. Simplest, and it is a route the plan already adds. *Preferred.*
* hook a `set_role` demotion — implicit, and surprising to whoever demotes.

## 4. The auth path

A new `_principal_from_user_key`, called from **`_authenticate`** (`security.py:849`,
covering both its call sites at `:857` and `:867`) — **not** inside
`_principal_from_key_checked`.

> Corrected after review. That function's docstring (`security.py:341-343`) states
> the invariant *"Nothing the store says can change a principal here — the lookup
> may only refuse one."* Minting a principal from the store there would break a
> documented rule, and would also run `_service_account_disabled`'s cached lookup
> against a human subject for nothing. Same outcome, invariant intact.

```
X-API-Key present
  ├─ starts with 'rsk_'  -> sha256 -> user store lookup by hash
  │     ├─ miss / revoked / expired      -> 401  (same body and timing as a bad env key)
  │     ├─ store error                   -> 503  (§2.4, never a principal)
  │     └─ hit -> Principal(tenant=<bound subject>, role=<usual sources>,
  │                         auth_method='user_key', key_id=..., scope=...)
  └─ otherwise -> existing env-map path, byte-identical
```

`Principal` gains `auth_method`, `key_id`, `scope` (all defaulting to today's
behaviour, so every existing construction site is unchanged). `__repr__` already
redacts `token`; the key value is never put on the Principal at all — only its id.

**Caching:** lookup is per request, memoized on `request.state` by the existing
`resolve_principal` memo. A ≤5 s positive cache may be added *only* with
revocation invalidation; if that proves fiddly, ship without it — a single
indexed lookup on a local sqlite/postgres is not the bottleneck, and a stale
positive is exactly what "revocable immediately" forbids.

**Go is a second consumer, and it will 401.** `go/internal/auth/auth.go:99-106,163`
resolves `X-API-Key` against env only, so an `rsk_` key is a 401 on every Go
route, and the five new routes are absent from its router — a chi **404**, not
the "501 behind the impl flag" the first draft assumed (only
`handler_document.go:37` 501s). Required: the contract's `ApiKeyAuth` scheme text
must say user keys are Python-only, and every conformance case must skip on
`RAGSTACK_IMPL=go`.

**Mint is bearer-only.** A key cannot mint a key. **Revoke is bearer-only with one
exception: a key may revoke itself** — useful for a script cleaning up, and
harmless since the caller already holds it. A stolen key therefore cannot delete
its victim's other keys.

## 5. Order of work

Reordered after review. Steps 0-2 are landable on their own and are worth doing
even if the feature is deferred.

0. **Set `operation_id="<contract id>"` on all 62 routes**, plus a test that the
   served ids equal the contract's. Currently **0 of 62 match** (§2.1). Without
   this the scope allowlist has nothing to key on. Independently valuable.
1. **Contract first** (house rule): OpenAPI + `contracts/schemas/*` for the five
   routes, `ApiKeyAuth` text saying user keys are Python-only. Moved up from
   step 5.
2. **`test_env_keys_are_unchanged`** before any production edit: the whole
   conformance suite green plus an explicit test that an env key's principal,
   role and error bodies are identical pre/post. 72 live keys depend on this;
   write it while the old behaviour is the only behaviour.
3. `scopes.py` + the allowlist test. No enforcement yet.
4. Store schema + protocol methods + the three backends.
5. **Startup prefix validation** (§2.3), next to `validate_role_settings()`
   (`deps.py:1578`). Before the branch, so the dispatch is total when it lands.
   Also require `identity_provider != none` when the flag is on — `_authenticate`
   still dispatches with the IdP off.
6. `_principal_from_user_key` in `_authenticate` (§4), behind
   `user_api_keys_enabled`, default **false**.
7. The five routes; scope-enforcement dependency; `auth_method`/`key_id` into
   `CONTEXT_FIELDS` and the request summary line (`context.py:65,85-87`).
8. **Decide the test harness before writing the cases.** Mint is bearer-only and
   the keyed conformance harness boots with no IdP, so the acceptance list
   *cannot run there as written*. Either bearer-only cases live in
   `python/tests/api/` (which has a fake-provider fixture,
   `test_identity_auth.py:47-54`) with conformance covering key *use* via a
   pre-minted key from env, or add a test-only provider with a startup guard that
   it can never be enabled alongside `REQUIRE_DURABLE_BACKENDS`.
9. Conformance + the no-leak canary. Docs: `docs/API.md`, user-guide "Scripting
   with your own key" — stating the workflow limitation of §2.2b plainly.
10. **Flip the flag on a `local`-backend tenant if ingest is part of acceptance.**
    Hackathon is `gowe`, so it proves query/retrieve/share and *cannot* prove
    ingest (§2.2b). asm or lucid proves the write path; hackathon proves the
    read path and is where the asking user is.

## 6. What could go wrong

* **The env path regresses.** 33 live keys depend on it; a break is a tenant-wide
  outage. Mitigated by step 1 and by the branch being additive and prefix-gated.
* **A scope hole.** A route that writes but is listed read-scoped. Mitigated by
  `full` being the default and by the contract test — but the allowlist still
  needs a human to read it once.
* **Timing oracle.** The miss path must match the env-key miss in body and
  roughly in cost; compare hashes with `hmac.compare_digest`.
* **A key outliving offboarding.** Mitigated by `revoke_all_api_keys` on
  `admin remove`/disable, tested.
* **Enumeration of `/v1/admin/users/{subject}/keys`.** Admin-only, and returns
  metadata only.

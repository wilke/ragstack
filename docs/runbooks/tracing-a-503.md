# Tracing a 503 — from a user's screenshot to the leg that was slow

The procedure for #427's own failure mode: a user reports "the search failed",
sends a screenshot, and you have to say *why* — which leg, which collection, how
long, and whether retrying is honest advice or a brush-off.

Before W1–W4 none of that was answerable. The access-log line and the error line
were unrelated rows, nothing timed a query, and a slow store and a slow LLM
looked identical. This runbook is the decision procedure over what those items
now record. It applies to any deployment running the shipped observability
stack (`v1.5.0` and later).

The worked example below is a **live run** of the acceptance test, 2026-08-27:
a store healthy at start-up, then stalled mid-request by a TCP proxy that
accepts the connection and never forwards — which reproduces the incident's own
class, a `ReadTimeout` rather than a connect failure. Tenant, user, collection
and store endpoints are templated; the ids and every timing are verbatim.

> The test rig ran `QDRANT_TIMEOUT=3` so a stall failed in seconds. Production
> runs **30 s**, or **60 s** on the two tenants serving the large collections.
> Read the ratios on the line, not the absolute 3 s.

---

## 1. Start from the screenshot — the `Reference:` id is the grep key

The error banner renders one line under the message:

```
Reference: 396fb7425f8748dc
```

Sixteen hex characters, generated by the server for this request. That is
`rid`. The banner deliberately shows *this* and never the server's own error
prose, which can name internal hosts, collections and settings — so the id is
usually all a user can give you, and it is enough.

If the user pasted the raw JSON body instead, the same value is
`"request_id"`. If they used `curl`, it is the `X-Request-Id` response header.
All three are the same id.

**No `Reference:` line at all?** The response carried no id. That is a much
narrower set of causes than "a 503": either the failure never reached the API
(the gateway answered), or it escaped through Starlette's own error middleware.
Check the gateway's log before the tenant's.

## 2. Grep the tenant's log for it

```
grep rid=396fb7425f8748dc /rag/data/tenants/<tenant>/logs/api-<tenant>.log
```

One request produces **one summary line**, plus whatever failure lines it
generated. For our example, two lines — the store failure, then the summary:

```
2026-08-27T12:33:40.929Z WARNING ragstack.api.main rid=396fb7425f8748dc
  tenant=<tenant>:<user> role=user route="POST /v1/query"
  store=qdrant reason=timeout elapsed_ms=3004 coll=<collection>
  msg="qdrant unavailable: qdrant search on '<collection>' at
       http://<qdrant-host>:<port> failed — ReadTimeout;
       per-request timeout is 3s (QDRANT_TIMEOUT)"

2026-08-27T12:33:40.930Z WARNING ragstack.observability.middleware
  rid=396fb7425f8748dc tenant=<tenant>:<user> role=user route="POST /v1/query"
  status=503 outcome=server_error wall_ms=3035.6 inflight=1 self_ms=2.2
  coll=<collection> qsha=a8f8b6d5
  authz_ms=5.7/1 embed_ms=24.0/1 rewrite_ms=0.0/1 vector_ms=3003.8/1
  by_coll="vector@<collection>=3003.8/1"
  embed_ep=http://<embed-host>:<port>/health
  msg="request complete"
```

(Wrapped here for width; on disk each is one logfmt line.)

`rid`, `tenant`, `role` and `route` are on **every** record the process writes
while a request is in flight, not just these two — so the same grep also picks
up any ad-hoc warning the request's code path emitted along the way.

The second line is the one you read. It answers, in order: *whose* request
(`tenant`/`role`), *what it cost* (`wall_ms`), *how busy the process was*
(`inflight`), *where the time went* (the `*_ms` stage fields), and *which
collection* (`coll`, and `by_coll` when a request fanned out).

Then look for the **retry**. Users retry; the retry is a different `rid` but the
same `qsha` and the same `coll`, seconds later:

```
status=200 outcome=ok wall_ms=164.3 vector_ms=20.3/1
```

That pair — 3003.8 ms then 20.3 ms on the same collection — is the whole
diagnosis, and step 3 is how to read it.

## 3. The decision table

Read `wall_ms` first, then find which stage accounts for it.

| What the line shows | Read it as | What to tell the user / do |
|---|---|---|
| `vector_ms` ≈ `wall_ms`, **`inflight` low**, and a fast retry on the same `coll` | **A cold read.** The store was not busy and was not broken; this request paid for warming, the next one did not. | Retry is the right advice, and it is honest — say so. Watch the rollup line (§8) for whether it is becoming routine. |
| `vector_ms` dominant, **`inflight` high** | **Contention, not the store.** The box was serving many requests at once; the vector leg is where the queueing surfaced, not where the fault is. | Do not chase the store. Look at concurrency and at what else was running (the same grep window, other `rid`s). |
| `gen_ms` dominant | **The LLM.** | Nothing to do with the vector store. Check the generation backend. |
| `rerank_ms` dominant | **The cross-encoder sidecar.** | Same — the store is fine. |
| `embed_ms` dominant | **The embedding fleet.** `embed_ep` names the endpoint that served this call. | Check that endpoint specifically; the pool picks least-loaded per call, so a single bad member shows up here and nowhere else. |
| `text_ms` dominant | **Elasticsearch**, the other half of a hybrid query. Instrumented since W2b — before that it was a bare 500 with a traceback. | Check ES, not Qdrant. |
| **`self_ms` large** | **The Python layer.** | Treat a surprising value as *suspect before acting on it* — see §5. This is the number ADR-0006's Go-port trigger reads, and it is an upper bound with two known inflators. |
| `reason=unreachable` on the failure line | **We never reached the store.** A `ConnectTimeout`/connection error, not a slow search — it fails in milliseconds against the same bound. | Retrying will **not** help. This is an outage or a misconfigured endpoint. The UI already says so (it withholds the warm-read promise for any `reason` other than `timeout`). |
| A 503 with **no `reason` field** at all | **Not a store failure.** The 503 on `/v1/query` is overloaded: authorization-store fail-closed, a dormant or restoring collection, or the tenant at capacity. Only the store-unavailable path emits `reason`. | Read `detail` and the surrounding lines. Two of those causes clear on their own. |

Two supporting fields:

- **`by_coll`** — per-leg attribution on a fan-out request, e.g.
  `by_coll="vector@<a>=1200.0/1 vector@<b>=45000.1/1"`. When a multi-collection
  query is slow, this says which collection, which `vector_ms` alone cannot.
- **`qsha`** — an 8-character SHA-256 prefix of the query text. It answers "was
  the request that 503'd the same query as the one that succeeded a minute
  later?" **The query text itself is never logged** (#114 mandates redaction by
  default); `qsha` is not reversible and is not a lookup key into anything.

## 4. What this cannot tell you — say it out loud

The instrument **rules concurrency in or out** and **rules the LLM, rerank and
embed legs in or out**. Both were impossible before #427.

It does **not** measure host page-cache state. So the first row of the table —
"a cold read" — is shorthand for a hypothesis, not a measurement. A cold page
cache and *an unlucky query vector touching more segments than usual* produce
the same line: `vector_ms` dominant, `inflight` low, a fast retry.

What changed is that this is now a **testable** hypothesis rather than an
unanswerable one. The retry's own line is the evidence: if the same `qsha` on
the same `coll` returns in 20 ms seconds later, warming is doing the work. If
retries are *also* slow at low `inflight`, warming is not the story and the
query-vector explanation gains.

Closing the question properly needs Qdrant-side telemetry on the store host —
segment-level search counters, page-cache residency — which is not this
repository. Do not report "cold cache" as a finding; report it as the surviving
hypothesis and say what would falsify it.

(#427 W9 adds an opt-in post-mortem probe for a *third* candidate this data
cannot see either: optimizer/indexing churn. It is off by default.)

## 5. `self_ms` is an upper bound, and on bearer deployments it is inflated

`self_ms` is `wall_ms` minus the **mean** of each recognised external stage. Two
deliberate conservatisms keep it an upper bound rather than a number that could
fire ADR-0006's trigger spuriously: means rather than sums (N concurrent legs of
9 s occupy 9 s of wall time, not 45 s), and an **unrecognised stage name is not
subtracted at all** — so a newly added external call inflates `self_ms` until
someone declares it external, rather than silently deflating the residual.

On top of that, **two external round trips in the dependency layer are inside
`wall_ms` and outside every stage**:

- `api/security.py` — `provider.authenticate` on the **bearer** path, a round
  trip to an identity provider;
- `api/security.py` — `_service_account_disabled` on the **API-key** path, a
  store read that is TTL-cached, so usually free and occasionally not.

Both therefore land in `self_ms`. On a bearer-auth deployment `self_ms` is
inflated by an unmeasured network call, and the handler-level test that pins the
stage-name set cannot see either of them, by construction.

**Before anyone quotes the residual at ADR-0006's trigger table**: either time
those two as `authz` first, or subtract them by hand, and note that a clean
residual wants a serialised (concurrency-1) measurement — a load test (#118) —
not a sample from production traffic. `self_ms` on a live line means "no more
than this".

## 6. Stage sums are sums; they do not add up to wall time

Every stage renders as `<name>_ms=<summed ms>/<observations>`, and **the
`/count` is never elided, even at 1**. Read it.

The query path nests `asyncio.gather` in three places — per query variant, per
collection, and per retrieval leg — so under fan-out the stage sums legitimately
*exceed* wall time. `vector_ms=45000.0/5` beside `wall_ms=9200.0` is **five
nine-second legs running concurrently**, not one forty-five-second search. The
`/5` is the only thing that distinguishes them, which is why it is always
printed and why `wall_ms` always sits on the same line.

Same rule for `colls=N` (how many collections a request targeted) and for
`by_coll`, whose per-entry values carry their own counts.

## 7. Turning the volume up — and back down again

`PUT /v1/admin/log-level` changes the level in this process **without a
restart** (admin-gated on every verb; the change is audited on a WARNING-pinned
logger so it cannot hide itself). It is process-local and resets on restart —
that is the feature. To make a level stick, set `LOG_LEVEL` and restart.

**Always send `ttl_seconds` with a DEBUG change** — DEBUG that turns itself off:

```
PUT /v1/admin/log-level   {"level": "DEBUG", "ttl_seconds": 900}
```

Bounds are 1..86400. `GET` reports `auto_revert_pending` and
`expires_in_seconds`, so you can see that the level will change under you.
`DELETE` reverts immediately.

Why the TTL matters here specifically: **DEBUG releases the dampened HTTP
transports** (`httpx`, `httpcore`, `elastic_transport`, `urllib3`). Those are
muted at INFO precisely so the summary line is readable — at DEBUG each outbound
call adds roughly 15 lines, and one `/v1/query` goes from ~3 lines to
**75–210**. On a busy tenant, DEBUG left on until the next restart is a disk
problem.

The opposite direction, `{"level": "WARNING"}`, is the quiet switch: it
**silences the INFO summary line and the rollup line** while keeping every
failure line — store failures, `server_error`, `unhandled`. Use it when an
operator asks for quiet, and know what you gave up: successful requests stop
being observable at all, so the "fast retry on the same collection" evidence in
§3 disappears with them.

> One documented hole in "WARNING keeps every failure": a 5xx whose response has
> already *started* and whose client then disconnects is recorded as
> `outcome=client_disconnected`, which is INFO by design (a user closing a tab
> is not a server fault and must not enter the error rate). Such a request's
> error line still appears as its own WARNING, but its summary line does not
> survive `LOG_LEVEL=WARNING`. Rare, and written down rather than left to be
> found.

## 8. The rollup line — is the bound creeping?

Every `LATENCY_ROLLUP_SECONDS` (default 300) the process emits one INFO line per
`(route, collection)` from an in-process histogram:

```
grep "latency rollup" /rag/data/tenants/<tenant>/logs/api-<tenant>.log
```

```
for_route="POST /v1/query" coll=<collection> n=412 errors=1
  p50_ms_le=250.0 p95_ms_le=5000.0 max_ms=3035.6 since_s=1800.004
  pid=31447 series=13 vector_p95_ms_le=5000.0
```

This answers the question a single request's line cannot: **is p95 moving toward
the timeout?** The incident that opened #427 exceeded its bound and nobody could
say whether that was normal-and-worsening or a one-off, because nothing kept a
distribution.

Three things to know before quoting it:

1. **The percentiles are bucket UPPER BOUNDS, not interpolations.** The field is
   named `p95_ms_le` — "p95 is at most 5000 ms" — because a bucketed histogram
   knows an observation fell in `(2.5 s, 5 s]` and does not know where. Never
   restate it as `p95 = 4213.7 ms`; that is precision this instrument does not
   have. The top bucket renders `inf`.
2. **The bucket boundaries straddle both bounds deliberately** — `… 10, 20, 30,
   60, 120` seconds, around the old 30 s `QDRANT_TIMEOUT` and the interim 60 s
   the two large tenants now run. Mass migrating out of the 2.5–5 s buckets into
   10–20 and 20–30 *is* the creeping-bound signal, and it is visible several
   windows before the first user sees a 503. That is the whole point of the
   line.
3. **It is per-process and cumulative over `since_s`**, which is elapsed seconds
   since this histogram started counting — not since the last line. Two rollups
   are diffable by their spans. `pid` is on the line because if `--workers` were
   ever added, the aggregate across processes is the ground truth and no single
   line is.

Also on the line: `n` and `errors` for the window, `series` (distinct
`(route, collection, stage)` keys held), and per-stage `<stage>_p95_ms_le`.
**`series_overflow` appearing on every row means the 512-series cap was hit and
the histogram is no longer complete** — new series were dropped rather than
recorded. It is printed on every row, not once, so it cannot be missed by
reading the wrong one.

Two restrictions worth knowing so you do not look for rows that were never
written: the histogram records only an **allowlist of parameter-free routes**
(`POST /v1/query`, `POST /v1/retrieve` — the raw path the middleware sees would
otherwise mint a series per ingest job id), and it does not record
`client_disconnected` at all. **The summary line still covers every route**;
only the histogram is restricted.
